# Issue 1085 JSONL filesystem boundary probe

The public `JsonlStorage::open` contract describes publication, recovery and poisoned-instance behavior, but does not specify whether the store directory or its ancestors may be symlinks. ADR 0075 targets Linux and forbids deleting user data. The architecture security section retains a no-follow policy; ADR 0057 describes tool path resolution, and ADR 0064's symlink-refusing parent walk applies to the separate application Session store. Those decisions do not by themselves specify the Durable directory compatibility contract.

The shared `JsonlStorage.cpp` helpers serve `main.jsonl`, document and task sidecars. Recovery enumerates the directory using `directory_iterator`, reads with `ifstream`, truncates partial and unconfirmed tails using `resize_file`, and uses path-based removal or temporary-file replacement for reclamation. Commits append sidecars then the main marker and reclaim after the marker is published; failed append poisons the instance, while reclamation after successful publication is best effort. Existing `ifstream`, `ofstream`, `resize_file` and directory traversal follow links. Numeric sidecar filenames prevent path injection but do not prevent filesystem aliasing.

Two independent temporary-directory public probes create a store-side `task-2.jsonl` alias to an outside file containing `complete\npartial`. A symbolic link and a hard link each cause `open` to fail only after truncating the outside target to `complete\n`: each test selected 1, passed 0, failed 1, skipped 0. The retained outputs are [symlink RED](1085-captures/symlink-red.txt) and [hard-link RED](1085-captures/hardlink-red.txt); trailing whitespace in the CTest output was removed. Both external targets were disposable test files. A task-only implementation subsequently rejects stable links; independent focused tests cover recovery and append for each alias. That implementation narrows the observed issue but did not solve the concurrent hard-link race or the existing main/document and store-directory risks; the reclamation, identity and descriptor-budget gaps below required a second pass.

A candidate Linux design opens and retains a directory descriptor for the store lifetime, enumerates relative to that descriptor, and uses single-component `openat` names with `O_NOFOLLOW`, `O_CLOEXEC` and `fstat` regular-file checks. Reads and their truncations must use the same file descriptor, and writes must open with no-follow at the actual append; replacement and deletion use descriptor-relative `renameat`/`unlinkat` so a terminal symlink is not followed. A checked descriptor avoids a `stat`/`open` race. In the current error model, unsafe or unreadable paths on open reject with a Validation corruption error; an append failure poisons the live instance. Reclamation still happens after marker publication and does not change a successful commit's result.

This design requires a decision about the store path: a final-component no-follow directory open leaves ancestor symlinks permitted; a no-follow parent walk rejects them and may change accepted input paths. Holding the descriptor protects against a later pathname replacement redirecting operations, but not mutation of the directory's entries by another process. A link count check can reject files already hard-linked at inspection; it cannot alone prevent another process from creating a hard link after that check. Frozen `packages/durable/README.md:682` states: “One process owns a storage at a time; there is no cross-process locking.” ADR 0075 says concurrent cross-process writers are not implicitly promised beyond upstream. Neither text rules out external filesystem mutation or defines it as trusted. The no-user-data-loss requirement therefore cannot be declared met for hard links and concurrent replacement on the basis of no-follow alone. Resolve the required trust and concurrency boundary or split the broader filesystem hardening work before claiming completion.

A separate frozen public `openNodeJsonlStorage` probe used the same stable aliases and disposable outside bytes. Frozen pi ignored the symlink and opened successfully without changing the target. It followed the hard link, truncated its partial tail and then raised `JsonlCorruptionError` on the malformed complete line; the outside target changed. The reproducible [probe](1085-captures/frozen-link-probe.mts) and [output](1085-captures/frozen-link-probe.txt) are retained. Rejecting a stable symbolic or multiple-link file without modifying it is therefore an intentional safety divergence, not frozen parity. Ordinary singly linked store files must remain interoperable and keep the published-prefix and error behavior described above.

The implemented task-only boundary captures a store directory descriptor at open and opens each `task-N.jsonl` with single-component `openat` plus `O_NOFOLLOW`, `fstat` regular-file and `st_nlink == 1` checks. Reads, torn-line and unconfirmed-tail truncation, and appends use the descriptor that passed the check. Recovery processes one sidecar at a time and does not retain a descriptor per sidecar; a bounded test lowers `RLIMIT_NOFILE` below a 64-sidecar store and requires recovery to succeed. Each observed file's device and inode are remembered. A later append to a name whose identity changed is refused and poisons the instance. Reclamation uses `fstatat` with `AT_SYMLINK_NOFOLLOW`, compares the entry with the observed identity, and only then calls `unlinkat` on the captured directory descriptor. A substituted symlink, hard link or plain file is left untouched; publication remains a successful commit if best-effort reclamation is skipped. After a successful `unlinkat`, or when `fstatat` reports the entry already absent, the remembered identity is erased. Otherwise the next commit for that task would create a new inode and fail the old identity check. With no remembered identity, a task commit creates the sidecar with `O_CREAT | O_EXCL`, so a file that reappears after reclamation is rejected rather than adopted and appended; with a remembered identity, `O_CREAT` is omitted so a vanished file is not silently recreated.

Three independent reclaim tests use disposable outside files. With a pre-fix implementation all three are discriminating failures: [reclaim identity RED](1085-captures/reclaim-identity-red.txt) shows a live update appended to a replacement file, substituted entries unlinked for all sections, an external file deleted through a replaced store path, and recovery failing under the reduced descriptor budget. The same selection [passes](1085-captures/reclaim-identity-green.txt) after the change: 4 selected, 4 passed, 0 failed, 0 skipped.

A later review found that successful reclamation left the old identity in the map. Reopening a store with an empty `task-2.jsonl` reclaimed the file, then a commit for task 2 created a new inode and poisoned against the stale identity. [stale-identity-red.txt](1085-captures/stale-identity-red.txt) shows the commit failing; [stale-identity-green.txt](1085-captures/stale-identity-green.txt) passes after erasing the identity on unlink or `ENOENT`. Erasing alone would let a file created externally between reclamation and the next commit be adopted by `O_CREAT` and appended. [replacement-red.txt](1085-captures/replacement-red.txt) shows that adoption and the external bytes changing; [replacement-green.txt](1085-captures/replacement-green.txt) passes with exclusive creation when no identity is known. A vanished-sidecar test covers the no-`O_CREAT` branch directly: after a live commit creates the sidecar and it is deleted externally, the next commit must fail closed and leave no file. The pre-fix `O_CREAT` path also poisons on the new inode, but only after recreating an empty sidecar; [vanished-sidecar-red.txt](1085-captures/vanished-sidecar-red.txt) records that failure and [vanished-sidecar-green.txt](1085-captures/vanished-sidecar-green.txt) passes after the change. The focused JSONL label then passed 28 of 28 with frozen `PI_CHECKOUT`.

Remaining limits are explicit. Trailing symlinks and hard links that were already present are refused before read or append, and reclamation never follows a final symlink; but a hard link created after `fstat` can still make the held descriptor's inode reachable by another name, and a replacement between `fstatat` and `unlinkat` cannot be rechecked by path. Capturing the directory descriptor means a later rename or symlink replacement of the store path cannot redirect task reclamation; it does not make `main.jsonl` or document sidecars descriptor-relative, and their existing path-based read, append, replace and remove behavior is unchanged. Ancestor symlinks in the original store path are followed when the descriptor is captured. Failure to reclaim remains best effort after successful publication and during recovery: the already-published terminal state opens, and the leftover sidecar is retried on a later open instead of turning cleanup failure into an open failure. The recovery test blocks `unlinkat` with a non-writable directory and skips when the process bypasses directory permissions (root or `CAP_DAC_OVERRIDE`); the pre-fix behavior fails the reopen. Normal singly linked files remain compatible. The directory and existing main/document paths need separate Owner-level design before expanding this change.

## Separate Storage batch difference

A [frozen public JSONL probe](1085-captures/frozen-terminal-live.mts) starts with an absent task ID 2, commits a terminal record followed by a pending record for that same ID in one batch, and observes seq 1 and pending `again` both immediately and after reopen ([output](1085-captures/frozen-terminal-live.txt)). The C++ StorageState rejects the batch as `Task is already terminal`; the original [C++ failing test output](1085-captures/terminal-live-red.txt) is retained. The new C++ check confirms its rejection is atomic and writes no task sidecar. Frozen Session `transaction.ts:465-466` rejects replacing a terminal candidate in one transaction, so this raw Storage batch is not reachable through that normal transaction path; no tested #1085 Harness continuation requires it. The JSONL reclamation plan uses the final write per ID, so accepting this batch retains the live sidecar. **Resolved by [#1168](https://github.com/lanshengzhi/cpp-coding-harness/issues/1168)** ([1168-terminal-live-batches.md](1168-terminal-live-batches.md)): the C++ terminal-replace invariant moved from shared StorageState to Session assembly, so all three backends now accept the frozen batch with the last write winning; this result still does not establish general Storage parity.

Verification includes independent outside-byte checks for task-sidecar links on read, recovery truncation, append and reclamation; normal recovery, marker failure, and publication with failed best-effort reclamation; and the bounded descriptor test. Preserve original evidence families and receipts. The corrected `audit-1085-replay` family is registered through the #1169 variant support; the original registered command remains defective and is documented, not replaced.
