# Issue 1085 JSONL continuation

## Scope

The tests exercise pi-v1.3.0 at `71023aec1546d6d677a65669c5665c0927ce0dd0` and the C++ Durable Harness over JSONL, using public Harness and transaction operations. The frozen checkout is supplied via `PI_CHECKOUT`; the live tests skip when it is absent and validate its clean revision before execution. No third-party plugins run.

## Observations and delivered behavior

Both directions create an unfinished task, queued input submission, and rewindable conversation document in the first runtime, close it, run the same task ID in the second runtime to checkpoint `finish/8`, close, and complete it in the third runtime with result 17. The middle runtime settles the original submission as unanswered with reason `aborted`. The document changes from `n=1` to `n=2` to `n=3`; the last C++ reopen reads current and historical values and the settled submission. In the pi→C++→pi case, pi also reads the original submission ID, request ID, status and reason before completion. Main marker sequences 1–7 and the intermediate task sidecar transitions are checked in that direction; C++→pi→C++ selects the pi document revision by its recorded sequence for historical reads.

Task sidecars are written before their main marker and confirmed by file, sequence and ordinal. Terminal records are inline and their task sidecars are reclaimed only after publication, on a best-effort basis. Recovery rejects missing or mismatched confirmed sidecars, discards an unconfirmed tail, and accepts missing historical task sidecars when a terminal marker supersedes them. One batch with two live updates preserves their ordinal order, and a subsequent live-to-terminal batch reopens terminal after reclamation.

A cross-runtime failure test saves the pi-created main and task sidecar, injects a real C++ main-marker append failure by replacing the main path with a directory, and observes a poisoned store and a longer unconfirmed sidecar. After restoring the original main bytes, C++ reopen truncates that tail and recovers the original pending checkpoint; pi then resumes the same task, and C++ reopens its advanced checkpoint. This is a controlled I/O failure, not a physical crash test. Separate tests check terminal-marker failure and recovery, and terminal reclamation. A separate test forces post-publication reclamation of a task sidecar to fail with a nonempty directory, verifies its child bytes survive and the commit remains successful, then removes the test obstruction and reopens the terminal result. Another test makes the store directory non-writable so recovery cannot unlink a leaked terminal sidecar; the published terminal state must still open, with the sidecar left for a later retry.

The original registered capture has a reproducibility defect: its recorded command omits a required output-directory argument. Integrity verification succeeds but does not execute this command. The original bytes and pin are preserved; [capture notes](1085-captures/README.md) retain the failure, independent captures and normalization rule. The corrected replay is registered as `audit-1085-replay` through the #1169 variant naming (`audit-<ticket>-<variant>`), leaving the original family and pin untouched. The original recorded command remains defective; the replay receipt does not repair it. Re-running the replay command succeeds, with only capture-time and generated-session differences from the pinned bytes ([notes](1085-captures/README.md), [rerun](1085-captures/replay-rerun.txt)).

## Remaining boundary

Stable task sidecar symlinks and multiply linked files are rejected without altering the target; this deliberately differs from frozen pi. Appends also require the observed file identity, and reclamation uses the captured directory descriptor with an identity check, so a replaced store path or substituted entry is not followed. Main/document paths and ancestor symlinks at open remain path-based, and a link created after inspection still races, as described in [filesystem boundary findings](1085-filesystem-boundary.md). Public Storage's terminal-to-live batch difference is tracked in [#1168](https://github.com/lanshengzhi/cpp-coding-harness/issues/1168); this slice does not establish general Storage parity. No claim is made for fsync failure, power loss, or multiple processes. These tests do not establish a capability beyond the exercised JSONL continuation slice; no capability status is promoted here.
