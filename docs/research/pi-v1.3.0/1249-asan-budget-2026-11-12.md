# #1249 ASan+UBSan lane budget, 2026-11-12

## Scope and observation

Item 3 of the #1249 triage: the `GCC 16 ASan+UBSan` matrix leg never
completed the suite on a cold or source-churned build — one attempt died
during Build and three were cut at the flat 90-minute job cap, two of them
mid-suite after ~36.6 and ~39.1 minutes of partial test signal (the
originally recorded "zero test signal" claim is corrected below). Only one
attempt, on a warm cache with little source churn, ran the suite to
completion. This pass diagnoses the build budget from CI logs, measures the
build locally, and lands a budget fix sized by those measurements. It does
not shard the suite (the alternative named in #1249): label sharding would
make every shard re-pay a full instrumented build on its own runner (measured
below at ~34 min cold / ~25 min warm each), so it is slower and costlier than
the budget fix for no signal gain; complementary blocked-label shards would
union back to the full suite, so narrowing the #473 "exercises the supported
test suite" contract is not a necessary consequence (also corrected below).

What the CI logs actually showed, run by run:

- `42986891227` (2026-11-11): Build ~39.8 min, then the suite ran ~36.6 min
  (through ~3515 of 4589 tests, job cancelled at ~90.2 min) — partial signal,
  not a silent run.
- `43162863923` (2026-11-12): Build ~37.5 min, then the suite ran ~39.1 min
  before the same ~90.2 min cap cancellation — partial signal.
- `43176359218` at `5a8375165` (2026-11-12, first run after the gate
  placement change, cold compiler cache): Build ran ~39 min, reached
  `678/681`, then died with exit 143 (SIGTERM, "ninja: build stopped:
  interrupted by user") at ~54 min into the job — *not* the 90-min cap. The
  sibling lanes in the same run concluded naturally with ordinary ctest exit
  8 failures, so the run was not cancelled.
- `43187786868` at `7ac7fb9ff` (warm compiler cache, little source churn):
  Build ~25 min, Gate 1 s, suite ~47 min, job total ~74 min. **4605 tests
  selected, 133 failed, exit 8 — the leg produces signal.** The failures
  include 113 `stack-use-after-scope` and 13 `heap-use-after-free`
  AddressSanitizer reports in product code (e.g.
  `cch::durable::Session::Impl::pump_line()`, `src/durable/Session.cpp:953`),
  which are real findings for separate defect lanes, not runner noise.
- `43224388351` at `f6b00f346` (warm caches but real source churn, which
  ccache cannot skip): Build ~40 min, suite started, and the job was cut by
  the 90-min cap **49.5 minutes into the suite** (cancelled at exactly
  ~90.25 min). Even the warm steady state no longer fits the cap once tests
  grow the suite — this is the decisive evidence for the budget fix.

## Correction (2026-11-12 independent review)

The independent review of this record found three misstatements, corrected
inline above and preserved here with what the GitHub logs actually show:

1. This record originally said the leg "produced zero test signal" and that
   `42986891227` and `43162863923` were "cut with no test step output".
   Verified against the run logs: both entered the suite and ran ~36.6 and
   ~39.1 minutes respectively before the ~90.2-minute cap cancellation
   (`42986891227` executed ~3515 of 4589 tests; `43162863923` reached the same
   shape). The correct distinction is partial signal versus no signal at all:
   the cap killed the runs mid-suite, so no completed suite exit code exists
   for a cold/churned build, but roughly the first three quarters of the suite
   did run and report.
2. "Cold build ~40 min + full suite ~47 min ≈ 89 min" was presented as the
   worst observed path. It is a spliced estimate assembled from different
   runs: the ~40 min builds belong to `43176359218` (whose build then died at
   678/681) and `43224388351` (whose suite the cap cut at 49.5 min), while the
   only full ~47 min suite ran after a ~25 min warm build in `43187786868`.
   No run observed a cold build plus full suite end to end. Accordingly, 150
   minutes covers that spliced estimate with ~60% headroom but cannot
   guarantee a cold build completes within budget, and it does nothing for
   the 54-minute SIGTERM on `43176359218` — runner memory pressure remains an
   unproven hypothesis, not a diagnosis.
3. Label sharding was said to "narrow the #473 contract". Complementary
   blocked-label shards union back to the full suite, so coverage narrowing
   is not a necessary consequence; the measured costs of sharding are the
   per-shard re-paid instrumented build (~34 min cold / ~25 min warm each)
   and the extra runner time.

The `timeout-minutes` comment in `.github/workflows/linux-toolchain.yml`
repeated the first two errors and is corrected in the same pass; the budget
value itself (150 minutes) is unchanged.

## Local measurement

Cold `vcpkg-asan-ubsan` build on this host (8 cores, build held to the
checked-in `jobs: 4` ceiling; GCC 16.2.1; vcpkg from the local binary cache):

- Wall time **2031 s (~34 min)**; CI measured ~39 min cold and ~25 min warm
  on 4-vCPU runners, so the local figure brackets the CI behavior.
- RSS sampled every 2 s across the whole build: peak `cc1plus` 2.35 GB, peak
  `ld` **3.79 GB**, with **up to three `ld` processes concurrent** (~2.4 GB
  each simultaneously at one point) during the closing link storm, plus
  `catch_discover_tests` discovery runs of freshly linked 0.5–1 GB test
  binaries. Machine-wide usage peaked at ~10 GB of 15 GB locally; a GitHub
  ubuntu-24.04 runner has 16 GB shared with the agent, so the cold overlap of
  2–3 links with straggling instrumented compiles plausibly exceeds it.

Mechanism, stated at the confidence the evidence supports: the 90-minute
kills are proven by the two runs stopping at ~90.2 min, mid-suite per the
correction above. The 54-minute SIGTERM is consistent with runner memory
pressure during the link storm (three ~3.8 GB `ld`s plus discoveries on
16 GB; the warm run with no compiles left to overlap survived the same
links), but it is a hypothesis, not a diagnosis — GitHub exposes no OOM
record. It is recorded here as the residual risk with its numbers so a
recurrence is diagnosed from data, not re-derived.

## Change

`.github/workflows/linux-toolchain.yml` only; no pinned input drift
(preflight: 838 pinned inputs, committed drift 0, uncommitted drift 0).

- `build-and-test.timeout-minutes` becomes `${{ matrix.timeout_minutes }}`
  (the matrix context is an allowed context for job `timeout-minutes`).
- Every leg keeps `timeout_minutes: 90`; the ASan+UBSan leg gets 150, with a
  comment carrying the measured evidence. 150 covers the spliced worst-case
  estimate (cold build ~40 min + full suite ~47 min + setup ≈ 89 min) with
  ~60% headroom for test-count growth; it is not a guaranteed bound — no cold
  build was ever observed to completion (the sole cold attempt died at
  678/681) and 150 minutes does not address the 54-minute SIGTERM.
- Sharding, quarantine additions, and build-system link pools were
  deliberately not taken: sharding is a net loss (see Scope), the 133
  failures are real findings #473 wants reported, and a `CMAKE_JOB_POOLS`
  link bound would touch `CMakeLists.txt` (34 pinned receipt inputs) — a
  follow-up lane if the SIGTERM recurs.

## Remaining boundary

The three cap-cancelled runs — two mid-suite at ~36.6 and ~39.1 minutes, one
(`f6b00f346`) 49.5 min into its suite — plus the one complete warm run and
the local measurement are the budget evidence: warm caches do not rescue the
cap once source churn or suite growth moves the build back to ~40 min. The
54-minute SIGTERM on a cold cache remains a supported-but-unproven OOM
hypothesis: the larger budget does not remove it — if it recurs, the measured
fix is a ninja link pool
(`CMAKE_JOB_POOLS` + `JOB_POOL_LINK`) or a per-leg build `--parallel` bound,
both of which trade build wall time for link memory. The 133 suite failures
(113 stack-use-after-scope, 13 heap-use-after-free) are product findings for
dedicated lanes; this change makes them visible instead of hiding them.
#1249 remains open for its other items; this record claims only the ASan
lane budget.
