# #1249 ASan+UBSan lane budget, 2026-11-12

## Scope and observation

Item 3 of the #1249 triage: the `GCC 16 ASan+UBSan` matrix leg produced zero
test signal — every attempt either died during Build or was cut at the flat
90-minute job cap before the suite ran. This pass diagnoses the build budget
from CI logs, measures the build locally, and lands a budget fix sized by
those measurements. It does not shard the suite (the alternative named in
#1249): label sharding would make every shard re-pay a full instrumented
build on its own runner (measured below at ~34 min cold / ~25 min warm each),
so it is slower and costlier than the budget fix for no signal gain, and it
would narrow the #473 "exercises the supported test suite" contract.

What the CI logs actually showed, run by run:

- `42986891227` (2026-11-11) and `43162863923` (2026-11-12): the leg ran
  exactly ~90.2 minutes and was cut with no test step output — the cap kill
  #1249 reported.
- `43176359218` at `5a8375165` (2026-11-12, first run after the gate
  placement change, cold compiler cache): Build ran ~39 min, reached
  `678/681`, then died with exit 143 (SIGTERM, "ninja: build stopped:
  interrupted by user") at ~54 min into the job — *not* the 90-min cap. The
  sibling lanes in the same run concluded naturally with ordinary ctest exit
  8 failures, so the run was not cancelled.
- `43187786868` at `7ac7fb9ff` (warm compiler cache, little source churn):
  Build ~25 min, Gate 1 s, suite ~47 min, job total ~74 min. **4605 tests
  selected, 133 failed, exit 8 — the leg produces signal.** The failures
  include 113 `stack-use-after-scope` and 13 `heap-use-after-free`
  AddressSanitizer reports in product code (e.g.
  `cch::durable::Session::Impl::pump_line()`, `src/durable/Session.cpp:953`),
  which are real findings for separate defect lanes, not runner noise.
- `43224388351` at `f6b00f346` (warm caches but real source churn, which
  ccache cannot skip): Build ~40 min, suite started, and the job was cut by
  the 90-min cap **49.5 minutes into the suite** (cancelled at exactly
  ~90.25 min). Even the warm steady state no longer fits the cap once tests
  grow the suite — this is the decisive evidence for the budget fix.

## Local measurement

Cold `vcpkg-asan-ubsan` build on this host (8 cores, build held to the
checked-in `jobs: 4` ceiling; GCC 16.2.1; vcpkg from the local binary cache):

- Wall time **2031 s (~34 min)**; CI measured ~39 min cold and ~25 min warm
  on 4-vCPU runners, so the local figure brackets the CI behavior.
- RSS sampled every 2 s across the whole build: peak `cc1plus` 2.35 GB, peak
  `ld` **3.79 GB**, with **up to three `ld` processes concurrent** (~2.4 GB
  each simultaneously at one point) during the closing link storm, plus
  `catch_discover_tests` discovery runs of freshly linked 0.5–1 GB test
  binaries. Machine-wide usage peaked at ~10 GB of 15 GB locally; a GitHub
  ubuntu-24.04 runner has 16 GB shared with the agent, so the cold overlap of
  2–3 links with straggling instrumented compiles plausibly exceeds it.

Mechanism, stated at the confidence the evidence supports: the 90-minute
kills are proven by the two runs stopping at ~90.2 min. The 54-minute
SIGTERM is consistent with runner memory pressure during the link storm
(three ~3.8 GB `ld`s plus discoveries on 16 GB; the warm run with no
compiles left to overlap survived the same links), but it is not proven —
GitHub exposes no OOM record. It is recorded here as the residual risk with
its numbers so a recurrence is diagnosed from data, not re-derived.

## Change

`.github/workflows/linux-toolchain.yml` only; no pinned input drift
(preflight: 838 pinned inputs, committed drift 0, uncommitted drift 0).

- `build-and-test.timeout-minutes` becomes `${{ matrix.timeout_minutes }}`
  (the matrix context is an allowed context for job `timeout-minutes`).
- Every leg keeps `timeout_minutes: 90`; the ASan+UBSan leg gets 150, with a
  comment carrying the measured evidence. 150 covers the worst observed path
  (cold build ~40 min + full suite ~47 min + setup ≈ 89 min) with ~60%
  headroom for test-count growth.
- Sharding, quarantine additions, and build-system link pools were
  deliberately not taken: sharding is a net loss (see Scope), the 133
  failures are real findings #473 wants reported, and a `CMAKE_JOB_POOLS`
  link bound would touch `CMakeLists.txt` (34 pinned receipt inputs) — a
  follow-up lane if the SIGTERM recurs.

## Remaining boundary

The two cancellation-labelled runs and the local measurement are the budget
evidence; the `f6b00f346` run adds the decisive third point — warm caches do
not rescue the cap once source churn or suite growth moves the build back to
~40 min. The 54-minute SIGTERM on a cold cache remains a supported-but-
unproven OOM hypothesis: if it recurs, the measured fix is a ninja link pool
(`CMAKE_JOB_POOLS` + `JOB_POOL_LINK`) or a per-leg build `--parallel` bound,
both of which trade build wall time for link memory. The 133 suite failures
(113 stack-use-after-scope, 13 heap-use-after-free) are product findings for
dedicated lanes; this change makes them visible instead of hiding them.
#1249 remains open for its other items; this record claims only the ASan
lane budget.
