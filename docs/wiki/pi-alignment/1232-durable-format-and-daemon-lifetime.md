## Remote self-join root cause and the shape of a fix, 2026-11-10

A 2026-11-10 read-only analysis of `src/codemode/Remote.cpp` at branch `t3/1232-witness-verify` (worktree `t3-1232-retirement`), commit `a82d9d35a` (`Bound remote retirement claims and preserve late exchange replies`), names the mechanism behind the recurring `Resource deadlock avoided` abort. `RemoteDeterministicServe` owns the joinable `std::thread worker` member, and the thread's own closure captures the same `shared_ptr` to that object (`served->worker = std::thread([served] { served->run->drive(); })`). The handle and the state the worker captures are therefore one object: the object is held alive by its own thread. When the worker's captured `shared_ptr` is the last strong reference, `~RemoteDeterministicServe` runs on the worker thread and calls `join()` on that same thread, which is `EDEADLK`, surfaced as `std::system_error: Resource deadlock avoided`. This analysis explains the GDB stack already recorded for the controlled red — last owner at the worker lambda's `shared_ptr` destructor, baseline `Remote.cpp:754` reached through `:842` — and adds no new run.

The recommended fix shape, recorded as an analysis rather than a validated patch, is to move the thread handle out of the shared state: the coroutine frame that creates the worker keeps it in a local RAII guard, so the last reference to `RemoteDeterministicServe` can die on any thread without that thread joining itself, and the guard's owner joins from a non-worker thread. Joining on the worker stays forbidden, and `detach` is not an acceptable substitute because it discards the only join witness. Two variants were ruled out at analysis time. Replacing `std::thread` with `std::jthread` alone changes nothing about the cycle: a `jthread` also joins in its destructor after requesting stop, so last-reference destruction on the worker is still a self-join. Moving the handle into the existing `RemoteWorkerReaper` first requires that reaper's admission and static-lifetime defects to be fixed, since that shape trades the known self-join for a stranded joinable handle, termination or an invalid-lifetime access depending on ordering (records at `t3/sandbox-timer-uaf-1232` @ `bae3a2b58`, uncommitted there: `1232-reaper-shutdown-cost-probe-2026-11-09.md` and `1232-explicit-worker-host-boundary-2026-11-09.md`; the latter also states that moving the handle into the same object under any other wrapper does not break the cycle).

This analysis sharpens the earlier "no production fix is proposed as safe" claims; it does not supersede them. The fix shape is not proved: a non-worker join still needs an owner whose lifetime encloses every creation, no discriminating test for that shape existed at `a82d9d35a`, and the host-boundary record at `bae3a2b58` still finds that the public interface hands no host, registration or shutdown operation to a caller.

## Staged-install failure: the isolation root is a hardcoded `/tmp`, 2026-11-10

The third full-run failure is test #4533 `staged install contains only the relocatable Runtime and behaves after relocation` (labels `cli;install;issue472;spec`), aborted after 2.70 s. The direct text is `REQUIRE( install.exit_code == 0 )` at `tests/cli/InstallRelocationTest.cpp:141`, expanding as `1 == 0`, with exactly three stdout lines and no stderr: the Debug configuration line, `Runtime install gate: PASS (Parity Architecture Gate, evidence freshness, dependency closure)`, and `-- Installing: /tmp/cpp-harness-catch2-1168379-295217015635951-0/tmp/cpp-harness-test-295217016421930/stage/bin/pike`. The failure is therefore at or immediately after the `file(INSTALL)` copy of `pike` into that stage prefix; Catch2 then aborted on its leftover-message assertion, which masks anything the installer would have printed later, and `run_command` (`InstallRelocationTest.cpp:54–65`) maps a signal death to the raw wait status, so the reported `1` cannot distinguish `exit(1)` from death by signal 1.

The write target follows from source: `tests/Catch2Main.cpp:84` builds the per-process isolation root from a hardcoded `const std::filesystem::path base{"/tmp"};` in `create_unique_root()` and sets `TMPDIR` to that root's `tmp` child, while `TempWorkspace` (`tests/support/TempWorkspace.hpp:14`) uses `std::filesystem::temp_directory_path()`. The install stage therefore resolves under `/tmp/cpp-harness-catch2-<pid>-…` regardless of the dedicated `TMPDIR` the full run exported, and an inherited `TMPDIR` cannot relocate it.

The single-case rerun passed against the same candidate build: 1 selected, 1 passed, 2.90 s, 99 assertions, no `/tmp/cpp-harness-catch2-*` leftover before or after. Its 1 s `df` samples show `/tmp` free falling from 8,262,279,168 to 7,825,428,480 bytes — a peak of 436,850,688 bytes (≈417 MiB), essentially the staged `pike` copy alone (the built binary is 435,800,376 bytes). `/tmp` is a 7.8 GiB tmpfs (8,309,002,240 bytes), so this case is a bounded ≈417 MiB consumer. The full run started with about 2.0 GiB free in `/tmp` and showed 1,661,800,448 bytes after it, but its guard polled only the checkout's root filesystem, so **free space at the failing instant was never sampled — that unrecorded minimum is the evidence gap**. Exhaustion is plausible against that headroom and is not established; transient concurrent `/tmp` use, tmpfs inode pressure and signal-induced death are not excluded.

Attribution: not the deterministic hunk. The failing `cmake --install` printed `Runtime install gate: PASS`, the same `build/pike` passed the case alone, and the candidate has no established path into install staging. Fix direction, in order: derive the isolation root from `std::filesystem::temp_directory_path()` keeping the unique-name retry loop and cleanup; add a pre-flight check on the filesystem that will actually hold that root, with an explicit floor and the chosen path reported, and/or monitor that filesystem's minimum during a full run; and treat the Catch2 leftover-message abort plus `run_command`'s signal/exit conflation as harness defects that hide the first cause. This is a direction, not a measured root cause.

## Test infrastructure parked: watchdog identity block, 2026-11-10

`docs/research/pi-v1.3.0/1232-watchdog-identity-safety-block-2026-11-10.md`, untracked in the local checkout `~/.cache/cch-timer-slice` on branch `timer-slice-1232` at `f2b027fc6` (no remote branch), records a containment decision: **do not run the old probes or previously built test binaries**. Two custom watchdogs are disabled at their source entry points, which now return explicit failures before creating a child.

The two defects are the same class: a numeric process group is signalled after its leader was reaped, so the identifier can have been reused. `TestProcessWatchdog.hpp` reaps the leader with a successful `waitpid` before `kill(-child, SIGKILL)`, and in the timeout path an unexpected wait error other than `ECHILD` also falls through to signalling without establishing continued ownership. `DeterministicStopProbe.hpp` reaps during handshake, release and completion, yet cleanup always signals the old process group; the injection pipe's `K` confirms only that a write happened after a kill, not that the helper exited; and on an unconfirmed injection the parent sends the helper SIGKILL but does not confirm its exit before it may reap the target. Either shape can signal an unrelated process. Retaining a zombie via `waitid(..., WNOWAIT)` is necessary but not sufficient, and a bounded wait cannot force a task in uninterruptible kernel sleep to exit.

The safe alternative exists only as a model (`1232-watchdog-identity-model-2026-11-10.md` and its `.py`, same branch), not as an implementation, and the block lists five obligations before re-enabling: exclusive reaping plus stable identity across every signal including SIGCHLD dispositions and setup failures; observe target exit without reaping and never signal a numeric ID after reaping or loss of ownership; confirm injector termination rather than acknowledgment delivery; hard-bounded isolated tests with simulated signal and reap events that never signal an unrelated real process; and independent review plus focused validation in the slice. Previously built binaries do not contain the source-level disable and stay unsafe. Consequence for this ticket: the stop-notify discriminating test above cannot lean on the old probe and watchdog tooling, which is why its phase gate remains unimplemented.

**(a) The self-join.** `RemoteDeterministicServe` is pure shared state again (`guest`, `queue`, `exchange`, `run`, `stop`), with no thread handle and no destructor. A frame-local `ScopedDeterministicWorker` (`src/codemode/Remote.cpp`) is declared immediately after `served`, so it destroys first while the frame still owns the state. Its destructor is a no-op when the handle is not joinable, requests stop on an unfinished run, calls `std::terminate()` if `worker.get_id() == std::this_thread::get_id()`, and otherwise joins. No path detaches, and `std::jthread` alone is not a substitute: its stop source is not the run's. Two observable changes are part of the contract: destroying a serve frame with an unfinished run now cancels and waits for it, and the serve's own `AsyncResult` completes only after the worker exits.

**(b) The lost stop wake.** `src/codemode/Deterministic.cpp` acquires and releases `shared.mutex` around the `stop_notify` call before `notify_all`, so the callback is paired with the mutex the worker holds while evaluating the false predicate of `shared.cv.wait(lock, ready)`.

**(c) The dependency loop.** `An abandoned serve frame stops and joins a deterministic run parked in the caller-answer wait` forces the window: the run is parked at the delivery loop's top, the frame's destructor reaches `finished()` while the mutex is free, is parked between that check and `request_stop()`, the worker then enters the wait predicate and is parked there, and only then is the request released. With the pairing reverted the case never returns — `ctest` reports `(Timeout)` at **30.04 s**, with the destroying thread in `join()` and the worker in `cv.wait`; with the pairing it measures **1.875–2.023 ms** over five sampled runs and **30/30** green, 27 assertions. The record also corrects the 2026-11-11 frame-join record's claim that the join "would then be unbounded" without that fix: the destructor's `finished()` takes `shared.mutex` before `request_stop()`, so the ordinary destruction path cannot land in the lost-wake window; the window needs the two acquisitions *separated*, which is what the case forces.

## Test isolation root and the ghost-failure mechanism, 2026-11-11

This is a diagnosis, not a fix. `tests/Catch2Main.cpp`'s `create_unique_root()` hardcodes `const std::filesystem::path base{"/tmp"};` (line 84) and only afterwards exports `TMPDIR` pointing at that root's `tmp` child (line 62). `TempWorkspace` (`tests/support/TempWorkspace.hpp`) does respect `TMPDIR` through `std::filesystem::temp_directory_path()`, so the tests' temporary trees still land under `/tmp/cpp-harness-catch2-<pid>-…`, i.e. on the 7.8 GiB tmpfs (8 309 002 240 bytes) instead of a caller-provided directory. Because a failing assertion in a `-fno-exceptions` translation unit runs no destructor, the isolation root is never removed on the failing path; each such failure leaks approximately 417 MiB, essentially the staged `pike` copy (435 800 376 bytes) plus notices. A case that passes alone therefore fails in a full run once enough earlier failures have consumed the tmpfs: the failure mode self-amplifies across a suite run.

Evidence: 37 `cpp-harness-catch2-*` directories were resident in `/tmp` at inspection on 2026-11-11 (that round counted 37–38), and each held exactly four entries — `home`, `tmp`, `xdg-cache`, `xdg-data` — which is the shape the isolation root creates and only its destructor removes. A directory holding exactly those four entries, still present, is the shape left when the destructor never runs.

Three harness defects hide the first cause. `INFO` pending at a failing assertion makes Catch2's leftover-message assertion abort the process, so the observable outcome is SIGABRT, not the condition that failed. `run_command` in `tests/cli/InstallRelocationTest.cpp` folded a signal death into the raw wait status (`WIFEXITED(status) ? WEXITSTATUS(status) : status`), so a reported code could not distinguish `exit(1)` from death by signal. And `create_directories` errors were discarded, so "no stderr" meant "nothing captured" rather than "nothing printed".

This does not affect CI: CI exports no `TMPDIR` and its runner's `/tmp` is on disk, so the hardcoded path lands on a large filesystem. It affects local full runs, which are exactly the runs whose failures this ticket's receipts depend on. The 2026-11-10 record's gap is unchanged: the free space in `/tmp` at the failing instant was never sampled, so exhaustion is a plausible mechanism, not an established one. No implementation is recorded here; at inspection on 2026-11-11 a lane named `test-tmp-root` held the checkout (since `2026-11-11T08:49:53Z`) and had uncommitted edits on the test tree (`tests/Catch2Main.cpp` and `tests/cli/InstallRelocationTest.cpp` among them) that this wiki does not describe or credit.
