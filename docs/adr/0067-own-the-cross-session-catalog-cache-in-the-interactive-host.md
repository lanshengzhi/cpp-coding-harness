# Own the cross-session tool-catalog cache in the interactive host

One `cch_mcp::UpstreamCatalogCache` is built by the interactive host — `run_native_tui_boot` calls `coding_agent::runtime::make_host_catalog_cache()`, the single constructor a frontend may name — and handed to every Agent Session that host creates, through the same `AssemblyOverrides` injection seam that carries the shared Models Runtime (ADR 0029/0030, issue #466). Threading a `std::shared_ptr` through `AssemblyOverrides` → `SessionFactory` → `McpSessionHostOptions` introduces **no `static` and no process-global mutable state**: it is the established `model_runtime` dependency-injection shape, and ownership is a value the host holds rather than a value the repository has somewhere. A host that runs one session and exits passes nothing, and such a session walks its own catalog exactly as it did before the cache existed. The `cch_mcp` type never crosses into a frontend: `make_host_catalog_cache()` lives in `cch_coding_agent` (`runtime/McpSessionHost.hpp`), and `src/coding_agent/tui/` and `src/coding_agent/cli/` name it only through a forward declaration, so ADR 0065's `frontend-no-direct-mcp-includes` is untouched (spec #833 story 17, issue #848).

**What this decision actually decides is the untrusted-descriptor lifetime policy.** A tool catalog is untrusted input whatever produced it: names, descriptions, JSON Schemas, and `x-mcp-header` annotations come from a third party. The `process` scope — the only scope in which a catalog may be reused across sessions — is a promise that those values stay live in a host-lifetime object and will be published into a **later** session's model context. Pike accepts that promise, under four limits that hold the exposure to what the Upstream itself authorized:

- **Only an Upstream that asked for it.** A catalog is admitted only when the Upstream supplied a freshness hint *and* declared `cacheScope: "process"`. An Upstream that says nothing is in the narrowest scope (`session`, `mcp::kDefaultCatalogCacheScope`) and is not admitted at all, so a session-scoped catalog is never served to a session that did not fetch it. The scope comparison is unchanged by this decision; sharing across sessions is what made the wider scope necessary, not a relaxation of the rule.
- **Only for the same Server Id *and* the same endpoint.** An entry is keyed by `(server_id, url)`, not by Server Id alone. A user who re-points a Server Id at another Upstream gets a cache miss and a fresh walk, never the previous endpoint's descriptors — the invalidation a cross-session cache owes, and the reason the key is a pair.
- **Only while the Upstream's own freshness hint holds.** `kMaxCatalogFreshness` caps a hint at 24 h; past it the entry is stale, the caller is served the best the Host has, and one bounded background refresh runs. Eviction is bounded at `kMaxCachedCatalogs` entries, oldest first, so bounding the cache can never silently disable it for a server the user still has.
- **Only for a Server Id the trust gate enables.** A Server Id whose consent is absent or revoked gets no connection at all, so its entry is never consulted; the `disabled` row is the whole of the answer.

Process exit is the remaining invalidation, and it is the reason this decision is scoped to a *host* rather than a session: the values live exactly as long as the process that was told about them, and no longer. Values that outlive the process would need a persistence decision this ADR does not make.

## Considered options

- **A `static` (or any other process-global) cache inside `SessionFactory` or `cch_coding_agent`**: rejected. It would be this repository's first process-global mutable state, its lifetime would be invisible at every call site, and it would be unreachable from a test without a reset seam invented for the test. CODING_STANDARDS §13.3 reserves ownership questions for an ADR rather than a code-level inference, and the ADR can grant the ownership to a named host without granting it to the process.
- **Leave `catalog_cache` caller-injected and unbuilt in production (what shipped in #848)**: rejected. Story 17 asks for repeated sessions not to re-list tools, and an unwired seam delivers none of it. The open question this decision answers — which long-lived object owns a cross-session cache, at what scope, with what invalidation — is a question an ADR is for, not a reason to ship the story unimplemented.
- **A `session`-scoped instance shared across sessions**: rejected. The cache admits an entry only when the catalog's own `cacheScope` equals its own, so a `session`-scoped instance shared between sessions would serve one session's catalog to a session that never fetched it — the contamination `cacheScope` exists to prevent.
- **Hold the cache on the Models Runtime**, the other host-lifetime value already threaded to every session: rejected. The Models Runtime is the AI/provider lifetime (ADR 0029/0030); an MCP catalog cache in it would make an unrelated owner responsible for an Upstream's trust and freshness, and would put a `cch_mcp` type on a path the `cch_ai`-facing runtime does not own.
- **One cache per `mcpServers` configuration hash, kept in a long-lived settings object**: rejected for v1. It is a more precise invalidation than the endpoint key, but it needs configuration identity that no seam publishes today; the endpoint key already answers the case that matters (a re-pointed Server Id) with no new state.

## Consequences

- `McpSessionHostOptions::catalog_cache` is filled in production, and `UpstreamCatalogCache::lookup`/`admit` take the endpoint as part of the key. `make_host_catalog_cache()` is the only place a `process`-scoped cache is built, and it is in the headless core so no frontend names a `cch_mcp` type.
- The interaction with Lazy Tool Activation (ADR 0066) is unchanged and additive: a published tool is registered once per session through the same between-turn drain, whether its catalog came from a walk or from a warm entry. A cross-session cache is invisible to every seam above the connection — status rows, trust, the tool binding, and the transcript are unaffected.
- The residual risk is the one this decision accepts by name: a warm entry published into a later session was walked by an earlier one. It is bounded by the Upstream's own `cacheScope` and freshness hint, by the endpoint key, and by the value-shaped rules the cache re-runs on admission (a catalog over the per-server tool cap, or one naming a tool twice, is refused). An Upstream that wants no cross-session reuse at all declares `session` or nothing and gets none.
- The bounds and their regression tests are recorded in `docs/runtime-capacities.md`; the cross-session behaviour is proven at the production door in `tests/coding_agent/McpCatalogCacheSessionTest.cpp` and at the cache itself in `tests/mcp/CatalogCacheTest.cpp`.
