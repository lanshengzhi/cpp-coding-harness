# Let the Agent own a mutable active tool loadout between Agent Turns

`cch::agent::Agent` gains exactly one tool-activation operation, reachable only through the private `cch::agent::detail::AgentToolAccess` adapter, that adds and removes one entry of its own registry; the active tool loadout is therefore mutable after construction, and mutable **only** at a turn boundary on the Agent's serialized execution domain — the one window in which no Tool Call Batch is resolving calls against the registry. The operation takes effect at the next Agent Turn boundary through the per-turn re-read of `run_policy.registry` that the turn machine already performs (`AgentRun.cpp`), so no request, executor, or projection path changes. The transcript remains the record of the loadout (ADR 0060 `toolsAdded`/`toolsRemoved`), and a resume replays the recorded set through the unchanged `replay_active_tool_names` filter. That filter only admits a name the live registry already holds, so a resume does **not** wait for Upstream tool discovery before the Agent is assembled — the recorded Upstream names are handed to the session's Upstream-tool binding as its restore set instead, and an activated Upstream tool becomes callable at the first turn boundary after its catalog lands, with no second restore path and no blocking wait on session start (spec #833 story 7, issue #847).

## Considered options

- **A shared mutable registry (`std::shared_ptr<ToolRegistry>`) held by both the session and the Agent**: rejected. It publishes a mutable shared object across an Owner Interface (CODING_STANDARDS §7.4 does not make `shared_ptr` an injection convention), invites a session-side write while a Tool Call Batch is mid-execution — `execute_single_call` holds a raw `Tool*` across a hook suspension, and an `unordered_map` insertion can rehash and invalidate it — and needs a mutex, which the zero-mutex contract (ADR 0051) does not admit.
- **An immutable registry snapshot swapped wholesale at a turn boundary (`std::shared_ptr<const ToolRegistry>`)**: rejected for this codebase. The design is correct in general, but `agent::Tool` is move-only by construction (`ToolExecute` is `std::move_only_function`), so a swap rebuilds every `definitions()` and map on each activation, `ToolCallExecutor` borrows `ToolRegistry&` and would have to be re-derived per batch, and `Tool*` stability for the in-flight rejection path is lost. The cost is disproportionate to the handful of activations a session performs.
- **A projection-side registry (the frontend keeps the activated list and the session filters at request time)**: rejected. The model-facing tool list is owned by `Agent::Impl::snapshot()` reading the live registry; a projection cannot influence it without pulling the frontend into the headless core's contract (ADR 0065's `headless-no-frontend-dependencies` and `frontend-no-direct-mcp-includes` rules), and it cannot produce the `toolsAdded` transcript entry, which is a session-store fact.

## Consequences

- `src/agent/ToolRegistry.hpp` gains one primitive, a per-name `remove`; `AgentToolAccess` gains the matching `remove_tool` beside the `add_tool` issue #842 added. No `Agent` signature changes, so every existing call site, the Owner Interface, and the Parity Gate's `no-agent-private-reach-through` evidence are untouched.
- The operations carry **no run-state guard**, deliberately: the between-turn window of a live run is exactly where a discovery or an activation must land (issue #842's between-turn publication), and the invariant that matters is that the set does not change while a Tool Call Batch resolves calls against it. The turn machine resolves a whole batch inside one turn, and the session's single drain is the only caller, so the window holds structurally rather than by a check somebody can forget. A caller that ever needs to change the set from outside that window must first make `ToolCallExecutor` hold a value instead of a borrowed `Tool*` — a larger change with its own ADR.
- Session startup still never blocks on an Upstream. A resumed transcript's recorded activation is restored through the existing drain at a turn boundary, so the tool set is complete from the first turn after its catalog lands rather than from the first turn of the session. This is the deliberate trade: no blocking wait on session start (spec #833 story 7, issue #841) in exchange for a window in which a resumed Upstream tool is named in the transcript but not yet callable.
- Activation is **sticky** for the session: a reconnect or a catalog-cache refresh replaces the staged value and never removes a live tool, because removing and re-adding a tool invalidates the provider's prompt cache (ADR 0064, spec #833 story 16).
- The two built-in meta-tools (`mcp_search`, `mcp_activate`) are staged through the same drain as any other discovered tool, so the whole product-visible effect of Lazy Tool Activation is `AgentToolAccess::activate` plus one ADR 0060 transcript record, and it is observable at the existing seams with no new one.
